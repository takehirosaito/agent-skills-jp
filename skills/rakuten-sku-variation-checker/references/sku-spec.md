# 楽天SKU・バリエーション仕様

最新仕様は RMS の商品登録画面で確認。

## 基本構造

```
親商品（商品管理番号）
├── 子SKU1（SKU番号）
│   ├── 選択肢タイプ（カラー）
│   ├── 選択肢項目（ブラック）
│   ├── 在庫数
│   ├── JAN
│   └── 価格
├── 子SKU2
│   ├── （ホワイト）
│   └── ...
└── 子SKU3
    └── ...
```

## 商品管理番号（親）

| 項目 | 仕様 |
|---|---|
| 列名 | normal-item.csv の「商品管理番号」 |
| byte | 32byte以内 |
| 文字 | 半角英数のみ |
| 一意性 | 店舗内で一意 |

## SKU番号（子）

| 項目 | 仕様 |
|---|---|
| 列名 | select.csv または item.csv の「SKU管理番号」 |
| byte | 32byte以内 |
| 文字 | 半角英数のみ |
| 一意性 | 親商品内で一意 |

## 選択肢タイプ

| タイプ | 用途 |
|---|---|
| プルダウン | 一般的なサイズ・色など |
| カラー | 色の見本付き |
| テキスト | 自由入力（名入れ等） |

## 選択肢項目

| 項目 | 仕様 |
|---|---|
| 表示名 | 顧客に見える名前（「Sサイズ」「ブラック」） |
| 内部名 | システム識別用 |

### 表示名のルール
- 楽天の標準命名に合わせる
- 表記揺れを避ける
- スマホで読みやすい文字数（5-10文字目安）

## 在庫管理

- SKU単位で在庫数管理
- 楽天は「在庫切れ」表示が自動的に出る
- 在庫1でも販売可、在庫0で自動的に選択不可

## CSVフォーマット

### normal-item.csv（親）

```csv
control,商品管理番号,商品名,キャッチコピー,...
n,SKU-PARENT-001,商品A,キャッチ,...
```

### item.csv または select.csv（子）

```csv
control,商品管理番号,SKU管理番号,選択肢タイプ,選択肢項目,在庫数,JAN,価格
n,SKU-PARENT-001,SKU-CHILD-001,カラー,ブラック,10,4901234567890,5000
n,SKU-PARENT-001,SKU-CHILD-002,カラー,ホワイト,15,4901234567891,5000
```

## バリエーション軸の組合せ

### 1軸（サイズのみ）
SKU数 = サイズ数
例：S/M/L/LL = 4SKU

### 2軸（サイズ × 色）
SKU数 = サイズ数 × 色数
例：4サイズ × 3色 = 12SKU

### 3軸以上
SKU数 = 各軸の数の積
例：4サイズ × 3色 × 2素材 = 24SKU

### SKU数の上限
- 楽天の仕様確認が必要
- 一般に1商品100SKU程度までが現実的
- 多すぎるとスマホ表示で選びにくい

## バリエーション間の価格差

- 同一商品内で価格差が大きいと不自然
- ±20%以内が目安
- 大きく違う場合は別商品検討

### 例
- S/M/L サイズで同価格 → OK
- 100ml 1,000円、500ml 4,000円（500ml が容量5倍だが価格4倍） → OK
- 通常版 3,000円、プレミアム版 10,000円 → 別商品検討

## JAN・カタログIDの管理

### 原則
- バリエーション間で **JANは別** にする
- 色違い・サイズ違いで同じJANはNG（重複扱い）

### 例外
- 海外輸入品で1JANしかない場合
- JANなしで管理する場合（受注生産等）

### Amazon連携時の注意
- Amazonは厳密にバリエーション間で別ASIN
- 同JANで複数バリエーションはNG

## 表示・選択UI

### スマホ表示
- プルダウン or タイル選択
- 在庫切れSKUは「在庫切れ」または非表示
- 色見本は画像で

### PC表示
- 同上、より広いレイアウト

## バリエーション変更時の注意

### 既存SKUの削除
- レビュー数・売上履歴の引き継ぎ確認
- 場合によっては新規登録の方が良い

### 新規SKU追加
- 既存親商品にSKU追加でOK
- 親商品名・キャッチが新SKUを含めて整合するか確認

### 親商品の置き換え
- レビュー・履歴のロスト
- 慎重に判断

## バリエーション設計のチェックリスト

新規登録・変更時：

- [ ] 商品管理番号が32byte以内、半角英数
- [ ] SKU管理番号が親商品内で一意
- [ ] 各SKUに在庫数が設定されている
- [ ] バリエーション間でJANが別になっている
- [ ] 選択肢名の表記が統一されている
- [ ] サイズ・容量が論理順に並んでいる
- [ ] 在庫切れSKUの扱いが決まっている
- [ ] スマホで選択肢が見やすい

## バリエーション機能を使わない方が良いケース

### 別商品にすべき
- 性別違い（メンズ・レディース）
- 旧モデル・新モデル
- 大幅な仕様違い
- セット商品と単品
- 価格差±50%以上
- ターゲットが異なる

### 別商品のメリット
- 性別ジャンル検索で両方拾える
- 個別のSEO最適化
- 在庫管理が独立
- レビューが商品単位で蓄積

### 別商品のデメリット
- 商品ページ作成・管理の手間
- 「同種商品があると分かりにくい」感
- レビュー分散

## バリエーションをまとめるメリット・デメリット

### メリット
- レビューが集約される（販売実績の総和）
- 商品ページ管理が一本化
- 顧客は1ページで全色・全サイズ確認可能
- 「色違いを並べて見たい」需要に対応

### デメリット
- 検索流入が一本化される（複数キーワードで取りにくい）
- 在庫管理が複雑
- 一部色だけ完売・補充が分かりにくい
