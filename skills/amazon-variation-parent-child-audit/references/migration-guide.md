# 既存ASIN の親子化／分離の手順

既存の個別ASIN を親子バリエーションに統合する、または既存の親子を分離する手順。

## ★最重要原則：「既存ASINの親子化は失うものが大きい」

| 項目 | 失う／引き継げない |
|---|---|
| レビュー | 子ASIN のレビューが新親に集約されない |
| 購入履歴 | 既存購入者の「再注文」リンクが切れる |
| 検索評価 | 既存ASIN のSEOランキングが下がる |
| 関連商品 | 既存ASINと紐づいていた関連商品リンクが切れる |
| ブックマーク | 顧客のリストに追加された旧URL が失効 |

→ 親子化は商品設計の初期に決めるのが鉄則。後の変更は慎重に。

## 親子化のシナリオ

### シナリオ1：個別ASINを親子に統合

**前提**
- 既存5ASIN（各色違いのシャツが別ASIN として登録済み）
- それぞれにレビュー20〜50件
- 1ヶ月平均10台販売

**選択肢A：既存ASIN を維持しつつ親子化**

```text
方法：
1. 新しい親SKU を作成
2. 既存5ASINを子に変更（parent_sku、relationship_type、variation_theme を追加）
3. フラットファイルでアップロード

期待結果：
- 既存ASINのURLは維持
- レビューが親に集約される（最新Amazon の動作確認必要）
- SEO評価は一時的に変動
```

**選択肢B：新親子セットを作成し、既存ASINを販売停止**

```text
方法：
1. 新親＋新子セットをすべて新規ASINで作成
2. 旧ASIN は quantity=0、または出品停止
3. 旧ASIN から新親へのリダイレクト依頼（カタログサポート経由）

期待結果：
- 旧レビューは新ASINには引き継がれない
- 新ASINでゼロから評価構築
- 既存購入顧客の再注文リンクは切れる
```

### シナリオ2：1ASIN内に混在しているのを分離

**前提**
- 1ASIN に複数色・複数サイズが混在登録
- レビューが商品違いで混在

**選択肢A：親子バリエーションに分離**

```text
方法：
1. 親SKU を作成（既存1ASIN を親として残す）
2. 子SKU を追加（各色・各サイズで新規ASIN）
3. 既存1ASIN は親として variation_theme 設定
4. 既存レビューは親に残る（混在レビューだが集約はされる）

期待結果：
- 顧客が選択UI で色・サイズを選べる
- 各バリエーションの在庫管理が個別に
- 既存レビューは混在のまま親に残る
```

**選択肢B：完全に分離してすべて別ASIN**

```text
方法：
1. 旧ASIN を販売停止
2. 各色・各サイズで新規ASIN
3. 親子関係を作るかは別途判断

期待結果：
- 顧客選択UI なし
- レビューが全色分散
- 一般的にはおすすめしない
```

## 推奨される親子化フロー

### Phase 1：分析・計画（1〜2週間）

#### Step 1：現状把握
- 統合対象ASIN リスト
- 各ASIN のレビュー件数・平均★
- 月間販売数・在庫
- 検索順位（主要KW）

#### Step 2：影響試算

| 影響項目 | 試算方法 |
|---|---|
| レビュー失効リスク | 統合前後で集約されるか確認（テストSKU で先行検証） |
| SEO影響 | 主要KW の現順位 → 統合後の予測順位 |
| 売上影響 | 移行期の売上低下を予測（一般的に10〜30%） |
| 顧客体験 | 選択UI の改善メリット |

#### Step 3：移行方式の選択
- 選択肢A（既存維持＋親子化）か B（新ASIN作成）か
- レビュー件数が多い場合は選択肢A 推奨
- レビュー件数が少ない場合は選択肢B も検討

### Phase 2：テスト実施（1週間）

#### Step 4：テストSKU で先行検証
- 既存ASIN とは別の小規模ASIN セットで親子化を試す
- 動作確認：選択UI、レビュー集約、検索表示
- 問題なければ本番へ

### Phase 3：本番移行（1〜2週間）

#### Step 5：本番フラットファイル作成
- 親行＋全子行のフラットファイル
- 既存ASIN を子として変換
- variation_theme、parent_sku、relationship_type を設定

#### Step 6：アップロード・反映
- セラーセントラルでアップロード
- 反映には数時間〜1日
- 反映後の動作確認

#### Step 7：移行期間中の運用
- 検索表示の確認
- レビュー集約の確認
- 顧客クレーム対応
- 売上トレンドのモニタリング

### Phase 4：移行後の検証（1〜3ヶ月）

#### Step 8：効果検証
- 統合前後の売上比較
- レビュー件数・★平均の推移
- 検索順位の推移
- カート投入率・CVR の変化

#### Step 9：問題対応
- レビュー集約が機能しない → カタログサポートに相談
- 検索順位低下 → SEO改善（タイトル・bullet・キーワード見直し）
- 売上低下 → 広告強化、価格戦略見直し

## 分離のシナリオ

### シナリオ：親子から個別ASINへの分離

**前提**
- 既存親子セット
- バリエーション間でブランドや機能が違いすぎる
- 「実は別商品」だった

**手順**
1. 親子関係を解除（フラットファイルで親子設定を空に）
2. 各子SKU を独立ASIN として運用
3. 各個別ASIN のページ品質を独立に管理

**注意**
- 親に集約されていたレビューは各子に分散
- レビュー★が薄まる可能性
- 慎重に判断

## 失敗事例

### 失敗1：レビューが集約されない
- 親子設定したのにレビューが各子に残ったまま
- 原因：variation_theme の親子不一致、parent_sku 参照ミス
- 対応：設定見直し、フラットファイル再アップロード

### 失敗2：検索順位の大幅下落
- 親子化後、主要KW の順位が大幅低下
- 原因：タイトル・キーワード変更の影響
- 対応：既存実績KW を可能な限り維持、A/Bテスト

### 失敗3：在庫切れ表示の不適切
- 1色だけ在庫切れだが、全体が「在庫切れ」に見える
- 原因：親の在庫表示ロジックの誤解
- 対応：在庫切れの子を quantity=0 にして販売停止、他子は通常販売

### 失敗4：URL 変更による顧客離脱
- 既存購入者のブックマーク・再注文リンクが切れる
- 原因：選択肢B（新ASIN作成）を選んだため
- 対応：選択肢A（既存維持）を採用する

## 移行コスト試算

### 工数
- 分析・計画：5〜10時間
- テストSKU 実施：3〜5時間
- 本番フラットファイル作成：5〜15時間（SKU数による）
- 動作確認：3〜5時間
- 移行後検証：継続

### リスクコスト
- 売上低下：通常10〜30%、3ヶ月程度で回復
- レビュー失効：シナリオによる
- SEO評価リセット：3〜6ヶ月で回復

### メリット
- 顧客選択UI の改善
- 在庫管理の効率化
- 検索結果での占有面積拡大（親ASIN として表示）
- レビューの早期集約

## 「移行しない」も選択肢

レビュー件数が多く、既存ASIN の評価が安定している場合：
- 個別ASIN のまま維持
- 新商品（次年度モデル）から親子化を開始
- 既存商品はそのまま運用

→ 移行コストとメリットを天秤にかけて判断。

## カタログサポートへの相談

複雑な移行はカタログサポートに相談：
- 「ASIN を統合したい」
- 「親子関係を再設定したい」
- 「レビューを引き継ぎたい」

詳細：`amazon-catalog-conflict-ticket-builder` スキル

## レビュー集約のメカニズム（最新の動作確認）

Amazon の親子レビュー集約は仕様変更があり得る：
- 最新の動作はセラーセントラルヘルプで確認
- テストSKU で先行検証
- 移行前に「想定通り集約されるか」を実機で確認

## 法的・税務的な注意

### 商品としての同一性
- 親子バリエーションは「本質的に同じ商品」が前提
- 「シャツ」と「Tシャツ」を親子化は無理
- 機能が違いすぎる場合は別ASIN

### 価格表示の整合性
- 親で「○○円〜」表示の場合、子の最安値が表示される
- 二重価格表示（景表法）に注意

### インボイス制度（適格請求書）
- 親子バリエーションでも、子単位で適格請求書発行事業者番号が必要
- インボイス対応の確認

## 移行プロジェクトの社内体制

| 役割 | 責任 |
|---|---|
| プロジェクトマネージャー | 全体管理 |
| カタログ担当 | フラットファイル作成・アップロード |
| 商品マネージャー | 親子設計の意思決定 |
| マーケティング | 検索KW・タイトル管理 |
| カスタマーサポート | 移行期の顧客対応 |
| 在庫管理 | 在庫の正確な反映 |
