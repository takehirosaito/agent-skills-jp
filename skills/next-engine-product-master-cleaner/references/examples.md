# ネクストエンジン マスタクレンジング ケース別実例

## ケース1：goods_id の表記ゆれと統合

### 入力

ネクストエンジン商品マスタCSV（抜粋、500件中）：

| goods_id | goods_name | zaiko_su | rakuten_item_code |
|---|---|---|---|
| TSH-001 | プレミアムTシャツ 黒 S | 6 | TSH-001 |
| TSH-001 | プレミアムTシャツ 黒 S | 7 | TSH-001 |
| tsh-001 | プレミアムTシャツ 黒 S | 0 | （空） |
| TSH_001 | プレミアム Tシャツ 黒 S | 0 | （空） |
| ＴＳＨ-001 | premiumTシャツ黒S | 0 | （空） |

### 検出

- 同一商品の意図で6パターンの表記ゆれ
- うち1件はzaiko_su=6でモール連携あり（楽天）
- 残り5件は在庫0、楽天連携なし → **過去のデータ移行や誤登録の残骸**

### 対応

1. **モール側の実態を確認**
   - 楽天RMS：商品管理番号 `TSH-001` が1件存在、在庫6
   - Amazon SP-API：item_sku `TSH-001` が1件存在、在庫7
2. **正規化先を決定**：`TSH-001`（大文字・半角ハイフン）
3. **その他5件を削除候補に**
4. **削除前の確認**
   - 過去受注データで `tsh-001` などの旧表記が使われていないか
   - 在庫0であっても会計上の在庫評価額に影響しないか
5. **段階削除**
   - まず `visible_flg=0` にして非公開
   - 1ヶ月運用して問題なければ削除

### 注意

- `TSH-001`（モール連携あり）の `goods_id` を変えない
- 統合は「他の表記ゆれを削除して `TSH-001` を残す」方向で

## ケース2：在庫加減算の事故予防

### 状況

「全商品の在庫を、仕入で増えた分だけ加算したい」

入力（仕入入荷分のCSV）：

| goods_id | 入荷数 |
|---|---|
| TSH-001 | 30 |
| TSH-002 | 20 |
| TSH-003 | 15 |

### 危険な手順（NG）

1. 商品マスタCSVをダウンロード
2. zaiko_su 列を「現在庫 + 入荷数」で再計算してExcel書き換え
3. 商品マスタCSVをアップロード

→ ネクストエンジンが「上書き」と解釈するか「加減算」と解釈するかで結果が変わる
→ Excel経由で他列も壊される可能性

### 安全な手順（推奨）

1. ネクストエンジン管理画面の「入荷登録」機能を使う
2. 商品コードと入荷数だけのCSVを別途用意（在庫変更専用フォーマット）
3. または管理画面で1件ずつ入荷処理
4. APIなら「在庫加算API」を使う

### 検証

- 入荷前の在庫スナップショット保存
- 入荷後の在庫を取得
- （入荷後在庫）= （入荷前在庫）+ （入荷数）を全件チェック

## ケース3：daihyou_shouhin_code の循環参照

### 入力

```
goods_id: A
  daihyou_shouhin_code: B

goods_id: B
  daihyou_shouhin_code: C

goods_id: C
  daihyou_shouhin_code: A
```

### 検出

`daihyou_shouhin_code` をたどると A→B→C→A→... と無限ループ。

### 原因

- 過去のデータ移行時の不整合
- 親子関係を後から組み替えて、片方の更新を忘れた

### 対応

1. 各商品の意図を確認
   - A は単品か？ バリエーション親か？ セット親か？
   - 同上 B, C
2. 構造を決定
   - 例：A がバリエーション親、B と C がバリエーション子
   - すべての `daihyou_shouhin_code` を A に統一
3. 修正
   - A: daihyou_shouhin_code = A（自身）
   - B: daihyou_shouhin_code = A
   - C: daihyou_shouhin_code = A
4. 検証
   - モール側のバリエーション構造とも整合するか

## ケース4：セット商品の在庫設計

### 状況

「赤ペン2本セット」「赤ペン3本セット」「赤ペン5本セット」を運用中。
赤ペン単品も販売中。
赤ペン単品の在庫が変動するとセット商品の販売可能数が連動。

### 入力

```
goods_id: PEN-RED
  set_flg: 0
  zaiko_su: 100

goods_id: PEN-SET-R2
  set_flg: 1
  構成: PEN-RED ×2
  販売可能数: 100 ÷ 2 = 50

goods_id: PEN-SET-R3
  set_flg: 1
  構成: PEN-RED ×3
  販売可能数: 100 ÷ 3 = 33（小数点切り捨て）

goods_id: PEN-SET-R5
  set_flg: 1
  構成: PEN-RED ×5
  販売可能数: 100 ÷ 5 = 20
```

### 検出

販売動作シミュレーション：

- PEN-SET-R5 が10個売れる → PEN-RED が 100 → 50
- 結果として：
  - PEN-RED 単品の販売可能数：50
  - PEN-SET-R2：50 ÷ 2 = 25
  - PEN-SET-R3：50 ÷ 3 = 16
  - PEN-SET-R5：50 ÷ 5 = 10
- セット販売が単品在庫を大きく消費する → モール側で在庫切れ表示の連鎖

### 対応

1. **販売予測に基づく在庫配分**
   - セット販売の比率を分析
   - セット用に「予約在庫」を確保する設計
2. **stock_goods_id の活用**
   - セット用と単品用で別の在庫管理単位を持つ（運用が複雑だが可）
3. **販売可能数の上限設定**
   - ネクストエンジン側でセット販売の上限を設定
4. **同期間隔の短縮**（プラン依存）

## ケース5：モール別SKU衝突

### 入力

ネクストエンジン商品マスタ：

| goods_id | rakuten_item_code | amazon_sku | yahoo_code | shopify_sku |
|---|---|---|---|---|
| TSH-001 | TSH-001 | TSH-001 | TSH-001 | TSH-001 |
| TSH-001-V2 | TSH-001 | TSH-001-V2 | （空） | （空） |

### 検出

- `rakuten_item_code = TSH-001` が**2件のネクストエンジン商品に紐付いている**
- 楽天で `TSH-001` が売れた → ネクストエンジンに2件候補があり、どちらに紐付くか不明
- 受注取込エラーまたは誤った商品の在庫が減算される事故

### 原因

- 旧モデル `TSH-001` を `TSH-001-V2` に切り替えた際、楽天SKUの紐付けを切り忘れ
- または、データ移行時の重複登録

### 対応

1. **どちらが現役か確認**
   - 楽天で実際に販売中のSKUを `TSH-001-V2` に変更
   - または `TSH-001-V2` のネクストエンジンマスタを削除（旧モデルなら）
2. **モール側SKUの一意性確保**
   - 1つの楽天 商品管理番号 = 1つのネクストエンジン goods_id
   - 多対1は事故の元
3. **連携設定の確認**
   - ネクストエンジン公式機能で「重複SKU検出」があれば活用

### 予防

- 月1回、モール側SKUとネクストエンジン側 rakuten_item_code 等の突合
- 不一致・重複を検出 → 即修正
- 新規商品登録時のバリデーション（rakuten_item_code の重複チェック）
