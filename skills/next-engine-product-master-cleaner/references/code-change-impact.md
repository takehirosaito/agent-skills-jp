# 商品コード変更時の影響範囲

ネクストエンジンの `goods_id`（商品コード）変更は、システム全体に広範囲な影響を及ぼす。**コード変更は最後の手段**で、代替策（表記ゆれの統合・新コードへの段階移行・履歴保持）を先に検討する。

## 影響範囲

### 1. モール連携

各モールに登録されている商品コード（楽天 商品管理番号、Amazon SKU、Yahoo! code、Shopify Variant SKU）との紐付けが切れる。

| モール | 影響 |
|---|---|
| 楽天 | 商品管理番号との連携が切れる → 在庫連動停止、受注取込でgoods_id不一致エラー |
| Amazon | item_sku との連携が切れる → 同上 |
| Yahoo! | code との連携が切れる → 同上 |
| Shopify | Variant SKU との連携が切れる → 同上 |

### 2. 在庫連携

- 在庫減算の対象が変わるため、現在の在庫数が引き継がれない場合あり
- 旧コードの在庫が「孤児在庫」として残る可能性

### 3. 受注処理

- 過去の受注データはgoods_idで紐付いている
- コード変更で「過去の注文 商品X」の表示が壊れる可能性
- 返品・交換・問い合わせ対応で旧コードを検索しても見つからない

### 4. 仕入・入荷

- 仕入先発注書のSKU
- 入荷時のスキャナバーコード（JAN含む）
- 倉庫管理システム（WMS）連携

### 5. 物流・発送

- ピッキングリスト
- 出荷ラベル
- 顧客への発送通知メール

### 6. レポート・分析

- 売上分析の連続性が切れる
- 在庫評価額の連続性
- カテゴリ別分析

## コード変更が必要になるケース

### よくある変更動機

1. **命名規則の刷新**：旧来のコードが煩雑で整理したい
2. **モール展開でコード統一**：複数モールに同じコードで出したい
3. **OEM切替**：仕入先が変わってコード体系も変わる
4. **M&A**：別ECからの統合
5. **桁数超過**：30字制約を超えるコードを既存運用してしまった

### コード変更の代替案

#### 代替案1：表示用コードと内部IDを分離

- 内部ID（goods_id）：システム的に動かない、機械的に振った番号
- 表示用コード（display_code 等）：人間が読むコード、自由に変えられる

→ 内部IDを動かさず、表示用コードだけ変更すれば影響は最小化

#### 代替案2：旧コードと新コードを両方保持

- 旧コードは履歴／検索用に残す
- 新コードを正式運用に
- ネクストエンジン公式機能で「旧SKU」「過去コード」を保持できる仕様があれば活用

#### 代替案3：段階移行

- 新規商品は新コード体系
- 既存商品は当面そのまま
- 廃番／再採番のタイミングで新体系へ移行

## どうしても変更する場合の手順

### 事前準備

1. **影響範囲の洗い出し**
   - モール側のSKU一覧を取得（楽天RMS / Amazon SP-API / Yahoo!ストアエディタ / Shopify Admin API）
   - WMS／物流／会計システムなど連携先のSKU依存箇所をリスト
   - 過去1年の受注データで旧コードがどれだけ使われているか
   
2. **新旧マッピング表の作成**
   - 旧コード ↔ 新コード ↔ JAN ↔ モール別SKU
   - 1対1で完全に紐付くか確認（1対多／多対1がないか）

3. **テスト**
   - テスト商品1件で新コードに変更
   - モール連携・在庫・受注が問題なく動くか確認
   - 在庫値が新コードに引き継がれるか

### 実施手順

1. **バックアップ**
   - 商品マスタCSV
   - 在庫データ
   - モール別SKU一覧
   - 過去30日分の受注データ
   
2. **モール側の作業**
   - 各モールでSKU変更可能か確認（一部モールはSKU変更不可・新規作成のみ）
   - 楽天：商品管理番号は変更可能だが再申請扱い
   - Amazon：SKUは変更不可、新規ASIN作成
   - Yahoo!：codeは変更可能
   - Shopify：Variant SKUは変更可能

3. **ネクストエンジン側の作業**
   - 「SKU統合」「コード変更」機能があれば利用（公式仕様確認）
   - なければ、新コードで商品マスタを新規作成→旧コードを廃番→在庫を新コードに移管
   
4. **連携テスト**
   - 1モールで新コード商品を1個販売
   - 受注がネクストエンジンに取り込まれるか
   - 在庫が新コードから減算されるか
   - 他モールにも在庫変更が反映されるか

5. **段階展開**
   - 少量商品から実施
   - 1日1モールずつなど慎重に

### 失敗時のロールバック

- バックアップから元のマスタを復元
- モール側のSKUを旧コードに戻す
- 在庫を旧コードに戻す
- 一時的に在庫連携を止めて手動同期

## コード変更を「避ける」ためのベストプラクティス

### 初期設計で決めるべきこと

1. **コード体系を最初に設計**
   - 30字以内、半角英数のみ、ハイフン区切り
   - バリエーション識別子の付け方（色×サイズ）
   - 仕入先・カテゴリ・年度のプレフィックス

2. **将来の拡張余地**
   - 桁数に余裕を持つ
   - 数値部に予備の0埋め

3. **モール展開を見越した命名**
   - Amazon ASINとの紐付け
   - 楽天の項目選択肢SKUとの整合

4. **表示用コードと内部IDの分離**

### 運用中のチェック

- 表記ゆれが発生していないか定期チェック（本スキルの主目的）
- 命名規則違反のコードがないか
- モールSKUと実態の照合を定期実施

## まとめ

| 変更動機 | 推奨対応 |
|---|---|
| 表記ゆれの統合 | SKU統合機能で履歴保持しつつ統合 |
| 命名規則刷新 | 表示用コードを別途設置、内部IDは固定 |
| モール展開でコード統一 | PIM側でモール別マッピングを保持 |
| 桁数超過 | 早急に変更（影響範囲を慎重に確認） |
| OEM切替 | 仕入先別の品番に新コード採番 |

商品コード変更は「**やる前に必ず影響範囲を洗い出し、代替策を3つ検討してから実施**」が鉄則。
