# 表記ゆれ検出パターン

ネクストエンジンの商品マスタで頻繁に発生する表記ゆれと、検出・正規化のパターン。

## 1. goods_id（商品コード）の表記ゆれ

### よくあるパターン

| 統一すべきコード | 表記ゆれ例 | 原因 |
|---|---|---|
| `TSH-001` | `TSH_001` | アンダースコア混入 |
| `TSH-001` | `tsh-001` | 小文字混入 |
| `TSH-001` | `Tsh-001` | 大文字小文字混在 |
| `TSH-001` | `ＴＳＨ-001` | 全角混入 |
| `TSH-001` | `TSH-001 ` | 末尾空白 |
| `TSH-001` | ` TSH-001` | 先頭空白 |
| `TSH-001` | `TSH–001` | EN-DASH混入 |
| `TSH-001` | `TSH−001` | MINUS SIGN混入 |
| `TSH-001` | `TSH−001` | 全角ハイフン混入 |
| `TSH-001` | `TSH-001​` | ゼロ幅スペース |
| `TSH-001` | `TSH-001\r` | 改行コード混入 |
| `0001234` | `1234` | Excel経由の0落ち |

### 正規化ルール

1. **両端の空白を除去**：`strip()`
2. **大文字統一**：`upper()` または小文字統一
3. **全角→半角**：英数記号の `unicodedata.normalize('NFKC', s)`
4. **ハイフン統一**：`-`（U+002D）に統一、他のハイフン類（U+2010-U+2015, U+2212, U+FF0D等）を置換
5. **ゼロ幅文字除去**：U+200B, U+200C, U+200D, U+FEFF 等を削除
6. **改行コード除去**：`\r` `\n` 除去
7. **アンダースコア→ハイフン**：必要に応じて統一

### 検出スクリプト例（Python）

```python
import unicodedata

def normalize_goods_id(s: str) -> str:
    if s is None:
        return ""
    # 改行・両端空白除去
    s = s.replace("\r", "").replace("\n", "").strip()
    # ゼロ幅文字除去
    for zwc in ["​", "‌", "‍", "﻿"]:
        s = s.replace(zwc, "")
    # NFKC正規化（全角→半角）
    s = unicodedata.normalize("NFKC", s)
    # ハイフン類を半角ハイフンに統一
    hyphens = ["‐", "‑", "‒", "–", "—", "―", "−", "－"]
    for h in hyphens:
        s = s.replace(h, "-")
    # 大文字統一
    s = s.upper()
    return s
```

### 検出

`normalize_goods_id` で揃えた結果が一致する元データを「表記ゆれグループ」として抽出。

## 2. 商品名の表記ゆれ

### よくあるパターン

| 統一すべき表記 | ゆれ例 |
|---|---|
| `Tシャツ` | `ティーシャツ`, `T-シャツ`, `ＴＳｈＩ`（全角混入） |
| `スマートフォン` | `スマホ`, `Smartphone`, `スマフォ` |
| `iPhone` | `アイフォン`, `iPhone`（全角I）, `Iphone` |
| `1,980円` | `1980円`, `1,980 円`, `１，９８０円` |
| `送料無料` | `送料込み`, `送料込`, `配送無料` |

### 正規化ルール（商品名は機械的に統一しすぎない）

商品名はSEOや検索の観点があるため、機械的な統一はリスクがある。代わりに：

1. **半角全角の混在を検出**（NFKC正規化後と元の差分）
2. **機種依存文字の検出**（SJIS外）
3. **絵文字の検出**
4. **末尾空白・改行の検出**
5. **同義語候補のレポート**（統一は人間判断）

## 3. JANの表記ゆれ

### よくあるパターン

| 統一すべき | ゆれ例 |
|---|---|
| `4901234567894` | `4.90123E+12`（指数表記） |
| `4901234567894` | `4901234567894.0`（末尾.0） |
| `4901234567894` | `4901-2345-6789-4`（ハイフン混入） |
| `0049012345678` | `49012345678`（先頭0落ち） |
| `4901234567894` | `４９０１２３４５６７８９４`（全角） |

### 正規化ルール

```python
import re

def normalize_jan(s: str) -> str:
    if s is None:
        return ""
    s = str(s).strip()
    # 指数表記対応
    if "E" in s.upper() or "e" in s:
        try:
            s = "{:.0f}".format(float(s))
        except ValueError:
            pass
    # 末尾.0除去
    if s.endswith(".0"):
        s = s[:-2]
    # ハイフン・空白除去
    s = re.sub(r"[-\s]+", "", s)
    # 全角→半角
    s = unicodedata.normalize("NFKC", s)
    # 数字のみ抽出
    s = re.sub(r"\D", "", s)
    return s
```

正規化後に8/12/13/14桁のいずれかになるかチェック。JAN-Check-Digit 検証は別スキル（`jan-code-checker`）で。

## 4. 価格の表記ゆれ

### よくあるパターン

| 統一すべき | ゆれ例 |
|---|---|
| `2980` | `2,980`, `2980円`, `￥2980`, `2980 円` |
| `2980` | `2980.0`, `2980.00` |
| `0` | （空欄）, `null`, `-` |

### 正規化ルール

- カンマ・通貨記号・空白を除去
- 数値化（整数または小数）
- 空欄は0または「未設定」として扱う（公開フラグ確認）

## 5. カテゴリの表記ゆれ

### よくあるパターン

| 統一すべき | ゆれ例 |
|---|---|
| `レディースファッション` | `レディース`, `女性向け`, `Ladies`, `女性服` |
| `食品` | `食料品`, `フード`, `Food` |

カテゴリは社内マスタで統一管理。表記ゆれを発見したら統一表に従って一括置換。

## 6. ブランド・メーカー名の表記ゆれ

### よくあるパターン

| 統一すべき | ゆれ例 |
|---|---|
| `Apple` | `アップル`, `apple`, `APPLE`, `Apple Inc.` |
| `ナイキ` | `Nike`, `NIKE`, `ﾅｲｷ` |

ブランド名はSEO・検索精度に直結するため統一が重要。社内マスタを準備。

## 7. 仕入先コードの表記ゆれ

社内コードでありながら、現場で勝手な略称が混ざることが多い：

- `S001` ↔ `S-001` ↔ `s001`
- 仕入先名の併記：`S001 山田商事` ↔ `山田商事 S001`

社内のサプライヤーマスタで統一。

## 8. 空白・不可視文字の罠

### 検出すべき不可視文字

| 文字 | Unicode | 影響 |
|---|---|---|
| 半角スペース | U+0020 | 末尾混入で別文字列扱い |
| 全角スペース | U+3000 | 同上、しかも見えない |
| ノーブレークスペース | U+00A0 | コピペ混入 |
| ゼロ幅スペース | U+200B | 完全に見えない |
| BOM | U+FEFF | ファイル先頭・列名先頭で事故 |
| タブ | U+0009 | CSVを破壊 |
| 改行 | U+000A, U+000D | 同上 |

### 検出スクリプト

```python
def find_invisible_chars(s: str) -> list[tuple[int, str]]:
    result = []
    invisibles = [" ", "​", "‌", "‍", "﻿", "\t", "　"]
    for i, ch in enumerate(s):
        if ch in invisibles:
            result.append((i, ch))
    return result
```

## 9. 表記ゆれレポートの構造

検出結果は以下の形式でまとめる：

```
表記ゆれグループ #001
  正規化後: TSH-001
  バリエーション:
    - "TSH-001" (3件)
    - "tsh-001" (1件)
    - "TSH_001" (2件)
    - "TSH−001"（全角ハイフン）(1件)
  推奨統一先: TSH-001
  影響: 楽天SKU "TSH-001"（一致）、 Amazon SKU "TSH-001"（一致）

表記ゆれグループ #002
  ...
```

## 10. 一括正規化のリスク

- **モール側SKUと一致しなくなる**：ネクストエンジン側だけ統一してもモール側で `tsh-001` のまま → 連携切れ
- **過去受注データとの整合**：旧表記の受注が新コードで検索できない
- **JAN紐付け**：JANを介した在庫共有が崩れる

→ **正規化は「ネクストエンジン側だけ」では完結しない**。モール側のSKU実態を取得してから判断する。

## 推奨運用

1. 月1回程度、本スキルで表記ゆれを検出
2. 検出後、モール側SKU実態を取得して照合
3. 統一案をレビュー（影響範囲確認）
4. 段階移行（1グループずつ、テスト商品→本番）
5. 統一後は新規登録時に正規化バリデーションを入れる
