# 多言語hreflang・海外SEO 設計

## 概要

多言語・多地域サイトの hreflang 設計と海外SEOを設計するスキル。「どの言語×地域を用意するか」「URLをどう分けるか」「hreflangをどこにどう書くか」を整理し、誤った言語版の表示・重複コンテンツ・インデックス漏れを防ぐ設計図を出す。越境EC（`shopify-markets-cross-border-setup`等）の国際化や多言語コーポレートサイトで使う。

## 最重要原則

**「言語と地域は分けて設計（en, en-US, en-GB 等）／hreflangは相互参照（双方向）が必須／x-defaultを用意／canonicalと矛盾させない／URL構成は最初に決めて一貫させる」**。hreflangは一方向だけ・自己参照漏れ・canonical不整合があると機能しない。実装の一貫性が最重要。

## 知識ベース

設計要素：

| 要素 | ポイント |
|---|---|
| 言語×地域 | `ISO639-1`言語＋必要なら`ISO3166-1`地域（en / en-US / en-GB） |
| URL構成 | サブフォルダ(/en/) / サブドメイン(en.) / 国別ドメイン(.de)。資産集約はサブフォルダが有利 |
| hreflang実装 | HTMLヘッドの`<link rel="alternate" hreflang>` / HTTPヘッダ / XMLサイトマップ のいずれか |
| 双方向参照 | 各版が全代替版＋自分自身を相互に指す |
| x-default | 言語選択ページや既定版を指定 |
| canonical | 各言語版はその版自身をcanonicalにする（別言語をcanonicalにしない） |

よくある失敗：
- 片方向のhreflang／自己参照漏れ
- canonicalを単一言語に集約してしまい他言語がインデックスされない
- 地域コードの誤り（言語コードのつもりで国コードを入れる 等）

> hreflang/canonicalの扱いは検索エンジンのガイドラインに従う。最新は各検索エンジンの公式ドキュメントで確認。

## 処理フロー

### Step 1：対象言語・地域の確認
- 提供する言語、地域差の要否（en-US/en-GBを分けるか）、対象市場
不明時は「日本語(既定)＋英語(en)＋必要地域」を仮置きし明示。

### Step 2：URL構成の決定
- サブフォルダ/サブドメイン/国別ドメインを選び、根拠（資産集約・運用・現地感）を提示。

### Step 3：hreflangマッピング設計
- 全ページ/テンプレート単位で、言語×地域の相互参照表を作成。x-defaultを定義。

### Step 4：実装方式の選定
- HTMLヘッド/HTTPヘッダ/サイトマップのどれで出すかを、サイト構成に応じて選定。

### Step 5：canonical・重複対策の整合
- 各版の自己canonical、パラメータ/重複URLの正規化、未翻訳ページの扱いを定義。

### Step 6：検証計画
- サーチコンソール等での国際化レポート確認、hreflang相互参照のテスト手順。

## 出力フォーマット

```
# hreflang・海外SEO 設計：[サイト]

## 0. 前提（言語×地域・仮定）
## 1. URL構成の決定と根拠
## 2. hreflang マッピング表（双方向＋x-default）
   | ページ | 言語×地域 | URL | 相互参照 |
## 3. 実装方式（ヘッド/ヘッダ/サイトマップ）
## 4. canonical・重複対策の整合
## 5. 検証計画（サーチコンソール/テスト手順）
```

## 品質ゲート
- hreflangが双方向＋自己参照＋x-defaultを満たすか
- canonicalが各言語版を自己参照し他言語に集約していないか
- URL構成が一貫しているか
- 地域/言語コードの取り違えがないか

## 注意事項
- 検索エンジンのガイドラインは更新される。最新公式を確認。
- 機械翻訳のみの薄いページは品質評価で不利になりうる。現地化を推奨。
- 本スキルは設計図を出す。実装・検証は環境に合わせて行う。
