# SKU命名規則 典型パターン集

## パターン1：シンプル連番（小規模・単一カテゴリ）

```
[ブランド]-[連番]
```

例：
- ABC-0001
- ABC-0002

**メリット**：
- シンプル、入力ミスが少ない
- 連番管理しやすい

**デメリット**：
- カテゴリ・バリエーションが見えない
- 後から軸を追加しにくい

**向く事業者**：
- 商品数100〜500未満
- バリエーションが少ない（カラー・サイズ展開なし）
- 単一カテゴリ

## パターン2：カテゴリ＋連番（小〜中規模）

```
[ブランド]-[カテゴリ]-[連番]
```

例：
- BRD-COS-0001（ブランドコスメ商品0001）
- BRD-FOOD-0001（ブランド食品商品0001）

**メリット**：
- カテゴリ別に管理可能
- 連番がカテゴリ内で完結

**デメリット**：
- バリエーションが見えない

**向く事業者**：
- 中規模（500〜2,000SKU）
- 複数カテゴリ

## パターン3：カテゴリ＋型番＋バリエーション（標準）

```
[ブランド]-[カテゴリ]-[型番]-[バリエーション]
```

例：
- BRD-COS-0001-30M（30ml）
- BRD-COS-0001-50M（50ml）
- BRD-AP-1500-BK-M（黒・M）
- BRD-AP-1500-WT-L（白・L）

**メリット**：
- バリエーション軸が明示
- ソートしやすい

**デメリット**：
- 桁数が増える（20文字程度）

**向く事業者**：
- 一般的なEC
- バリエーション展開ある

## パターン4：年度＋シーズン＋型番（季節商品多い）

```
[ブランド]-[年度]-[シーズン]-[型番]-[バリエーション]
```

例：
- BRD-24-SS-1001-BK-M（2024春夏・型番1001・黒・M）
- BRD-24-AW-2050-NV-L（2024秋冬・型番2050・紺・L）

**メリット**：
- 年度別・シーズン別に整理
- 旧モデルとの区別が明確

**デメリット**：
- 桁数が長い
- 年度を跨ぐ商品の扱いが複雑

**向く事業者**：
- アパレル
- 季節商品が多い
- 年度ごとに商品ライン更新

## パターン5：構造的なメーカー型番（家電・精密機器）

```
[ブランド]-[シリーズ]-[モデル]-[グレード]-[カラー]
```

例：
- BRD-AC-PRO-PLUS-WT（ACシリーズ Pro Plus 白）
- BRD-AC-LITE-STD-BK（ACシリーズ Lite 標準 黒）

**メリット**：
- メーカー型番と整合
- スペック識別しやすい

**デメリット**：
- シリーズ名・グレード名のルール作りが必要

**向く事業者**：
- 家電
- 精密機器
- 自社オリジナル製造

## パターン6：マルチブランド（複数ブランド運用）

```
[ブランドプリフィックス]-[カテゴリ]-[型番]-[バリエーション]
```

例：
- BRD-COS-0001-30M（自社ブランド略号）
- BTN-COS-0001-30M（ボタンブランド）

**メリット**：
- 複数ブランドが共存可能
- ブランド別の分析が容易

**デメリット**：
- ブランドプリフィックスの命名規則が必要

**向く事業者**：
- 複数ブランド展開
- OEM＋自社ブランド

## パターン7：軽量シンプル（テスト商品・新規）

```
[シンプル文字列]
```

例：
- TEST001
- NEW-2024-001

**メリット**：
- 命名負荷低い
- 一時運用に最適

**デメリット**：
- 長期運用に不向き

**向く事業者**：
- テストマーケティング
- 短期キャンペーン商品

## 命名規則の比較表

| パターン | 桁数 | 拡張性 | 可読性 | 向く規模 |
|---|---|---|---|---|
| 1. シンプル連番 | 8 | △ | △ | 〜500 |
| 2. カテゴリ＋連番 | 12 | ◯ | ◯ | 500〜2,000 |
| 3. 標準 | 20 | ◎ | ◎ | 2,000〜10,000 |
| 4. 年度・シーズン | 22 | ◎ | ◎ | 季節商品 |
| 5. 構造的型番 | 18 | ◯ | ◎ | 家電 |
| 6. マルチブランド | 22 | ◎ | ◎ | 複数ブランド |
| 7. 軽量 | 8 | × | △ | テスト |

## 桁数の決め方

### モール文字数制限
- 楽天商品管理番号：半角英数字、アンダースコア、ハイフン使用可（255バイト以内）
- Amazon SKU：40文字以内推奨（半角英数字・ハイフン・アンダースコア）
- Yahoo! 商品コード：半角英数字、最大128文字程度
- Shopify Variant SKU：制限緩い
- Google Merchant Center：固有のID必須

実務上は**30文字以内**に収めると安全。

### 連番桁数の目安

| 想定SKU数 | 連番桁数 |
|---|---:|
| 100以下 | 3桁（000-999） |
| 1,000以下 | 4桁（0000-9999） |
| 10,000以下 | 5桁 |
| 100,000以下 | 6桁 |

将来拡張を見越して1桁多めに取る。

## 区切り記号の選び方

### ハイフン「-」（推奨）
- 半角英大文字＋ハイフンが最も互換性高い
- Excel・CSV・モール仕様にすべて適合

### アンダースコア「_」
- システム名・変数名で頻出
- ハイフンと混在禁止

### ピリオド「.」
- ファイル名と紛らわしい
- 推奨しない

### スラッシュ「/」
- URLの一部と認識されるリスク
- 使わない

### スペース
- 絶対NG（モール仕様で弾かれる）

## 桁数固定のメリット

ゼロパディング（先頭を0で埋める）で桁数固定：
- 001, 002, 003, ..., 099, 100, ..., 999

**メリット**：
- ソートしやすい（文字列ソートで数値順）
- 視覚的に揃って見やすい
- 一目で連番桁数の上限が分かる

**デメリット**：
- 上限超過時の桁数追加が手間（999→1000）

## 軸の追加可能性

将来軸を追加する場合：
- 既存SKUを変更しない
- 新規SKUから新軸を採用
- 例：「BRD-SK-0001」のあるブランドが、後から年度軸を入れたい場合、
  - 既存：BRD-SK-0001
  - 新規：BRD-24-SK-0050
  - 移行期間中は両方並走

または、新軸が出るタイミングで全SKU命名を見直す（リスク高い）。

## 既存SKUの移行プラン

### 一括移行
- リスク：モール検索順位リセット・売上履歴の見え方変化
- メリット：体系統一

### 段階移行
- 新規商品から新体系を適用
- 既存商品は移行せず、サポート列で対応

### マッピング表方式
- 旧SKUと新SKUの対応表を保持
- システム上で両方検索可能に

実務上は「**新規商品から新体系・既存は変更しない**」が現実的。
