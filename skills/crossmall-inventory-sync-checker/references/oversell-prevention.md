# ダブル販売リスクと安全在庫設計

## ダブル販売（オーバーセール）とは

在庫1個の商品が、複数モールで同時に受注成立してしまう事故。連携間隔（30-60分）の隙間に発生する。

### 発生メカニズム

タイムライン例（在庫1個、連携間隔30分）：

```
14:00 楽天とAmazon両方で在庫1個と表示
14:05 楽天で1件受注 → 楽天側在庫0、クロスモールはまだ未同期
14:10 Amazonで1件受注 → Amazon側在庫0、両モール「成立」
14:30 クロスモール同期 → 受注2件を取り込み → 基準在庫 1 - 2 = -1
14:30 楽天/Amazon在庫を 0 に上書き
14:31 倉庫：物理在庫1個に対し、2件の出荷指示 → 1件キャンセル必須
```

### 影響

- 顧客にキャンセル連絡 → 信用毀損
- 顧客対応コスト
- レビューでの評価ダウン（特に楽天・Amazon）
- アカウント健全性スコアの悪化（Amazonは特に厳しい）
- 売り越し対応の業務負荷

## 安全在庫設定の戦略

### 基本式

```
モールに表示する在庫 = 実在庫 - 安全在庫
```

実在庫10、安全在庫1 → モール表示9
売れたら：実在庫9、モール表示8

実在庫が安全在庫を下回ったらモール側「在庫切れ」表示。

### 商品別の安全在庫設定

| 商品特性 | 安全在庫の目安 | 理由 |
|---|---|---|
| 高速回転（日次10個以上売れる） | 2-5 | 連携間隔内に複数販売が想定される |
| 中速回転（週次10-30個） | 1-2 | 同時受注リスクは中程度 |
| 低速回転（月次1-10個） | 0-1 | リスク低、安全在庫で機会損失したくない |
| 在庫1個の希少品 | 0（または1モールに集約） | 安全在庫1にすると即在庫切れ表示 |
| 高単価商品 | 1-2 | キャンセル時の影響が大きい |
| 予約販売・取り寄せ | 設定不要（受注後発注） | 在庫概念がない |

### 安全在庫を 0 にする条件

- 月次販売数が少ない（5個以下/月）
- 在庫切れによる機会損失が安全在庫のメリットを上回る
- 在庫1モール集約で代替できない

### 安全在庫を 3 以上にする条件

- 日次販売数 30以上
- 同時受注が頻繁
- ダブル販売事故が直近で発生済み
- 高単価かつ希少（キャンセル時の影響大）

## 1モール集約戦略

### いつ使うか

- 在庫1個の高単価／希少商品
- 連携間隔が長く、安全在庫設定でも事故が止まらない
- Amazon FBA のみで販売

### 集約のメリット
- ダブル販売リスク0
- 在庫管理がシンプル

### 集約のデメリット
- 他モールでの販売機会喪失
- マーケティング露出の減少

### 集約モールの選び方

- **Amazon FBA**：在庫実時刻反映、ダブル販売は基本起きない
- **Shopify**：自社ECで在庫管理が綿密にできる
- **楽天 / Yahoo!**：連携前提で運用するなら集約には不向き

## リアルタイム連携への移行

### 利用可能なモール

- **Amazon SP-API**：在庫変更APIをリアルタイム呼出 可
- **Shopify Admin API**：ほぼリアルタイム
- **楽天 RMS Web Service API**：在庫API、頻度制限あり
- **Yahoo!ショッピングAPI**：在庫API、頻度制限あり

### 実装方法

クロスモールが対応していれば設定で切り替え。対応していなければ：
- 自社API実装（受注Webhookで即在庫反映）
- サードパーティのリアルタイム連携サービス

### 制約

- API呼出制限（モール毎に1秒数回まで）
- 大量商品（数千SKU）の即時連携はAPI制限で困難
- 高頻度更新商品に限定して使うのが現実的

## 監視と対応

### モニタリング指標

1. **マイナス在庫件数**（基準在庫が負）
2. **キャンセル率**（在庫不足によるキャンセル）
3. **ダブル販売事故件数**
4. **連携失敗ログ**

### アラート設定

- マイナス在庫発生 → 即時通知
- 連携失敗 → 即時通知
- キャンセル発生 → 日次集計

### 事故対応フロー

1. **検知**：基準在庫マイナス、または顧客からの問合せ
2. **特定**：どのモールの受注が、いつ、何個成立したか
3. **判断**：どの受注をキャンセルするか（早い者勝ち／単価高い順／顧客ランク）
4. **顧客連絡**：丁寧な謝罪、代替提案、お詫びクーポン等
5. **再発防止**：該当商品の安全在庫見直し、連携設定確認

## 安全在庫の動的調整

固定値ではなく、販売速度に応じて自動調整：

```python
def calculate_safety_stock(daily_sales: float, mall_count: int, sync_minutes: int) -> int:
    """
    daily_sales: 過去30日の平均日次販売数
    mall_count: 連携モール数
    sync_minutes: 連携間隔（分）
    """
    # 連携間隔中に売れる可能性のある数
    interval_sales = daily_sales * (sync_minutes / (60 * 24))
    # 複数モール同時販売の余裕
    safety = interval_sales * mall_count * 1.5
    return max(0, int(safety))
```

例：日次10個、3モール、同期30分
- interval_sales = 10 × (30/1440) = 0.208
- safety = 0.208 × 3 × 1.5 = 0.94
- → 安全在庫 1 個

日次30個、3モール、同期30分
- interval_sales = 30 × (30/1440) = 0.625
- safety = 0.625 × 3 × 1.5 = 2.81
- → 安全在庫 3 個

## 業務運用のチェックリスト

- [ ] 全商品の販売速度を計測している
- [ ] 高速回転商品に安全在庫が設定されている
- [ ] マイナス在庫アラートが設定されている
- [ ] 連携失敗ログを毎日確認している
- [ ] 月次でダブル販売事故件数を集計している
- [ ] 高単価商品はリアルタイム連携または1モール集約を検討した
- [ ] キャンセル発生時の顧客対応フローが整備されている
