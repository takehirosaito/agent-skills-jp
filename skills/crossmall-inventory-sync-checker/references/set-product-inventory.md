# セット商品の在庫整合

セット商品（組商品）は「複数の単品を組み合わせて1販売単位とした商品」。在庫管理が複雑で、連携事故が起きやすい。

## セット商品の在庫モデル

### 基本構造

```
子A: PEN-RED（在庫50）
子B: PEN-BLUE（在庫30）
セット親: PEN-SET-RB（構成: PEN-RED ×1, PEN-BLUE ×1）
  販売可能数: min(50, 30) = 30
```

### セット販売時の動作

セット親が1個売れる：
- PEN-RED の在庫：50→49
- PEN-BLUE の在庫：30→29
- セット親の販売可能数：min(49, 29) = 29

### 複数セットが同一子を共有する場合

```
子: PEN-RED（在庫100）
セット親A: PEN-SET-R2（構成: PEN-RED ×2）→ 販売可能 50
セット親B: PEN-SET-R3（構成: PEN-RED ×3）→ 販売可能 33（小数切捨）
セット親C: PEN-SET-R5（構成: PEN-RED ×5）→ 販売可能 20
```

セット親Aが1個売れる：
- PEN-RED の在庫：100→98
- セット親A：50→49
- セット親B：33→32
- セット親C：20→19

連動関係が複雑になるため、連携設定での「**構成情報を正しく登録**」が必須。

## クロスモールでのセット商品の扱い

### 設定方法（一般）

クロスモール側で「組商品」または「セット商品」として登録：
- セット親の商品コード
- 構成元（子）のSKUと数量

例：
```
セット親: PEN-SET-RB
  構成:
    PEN-RED ×1
    PEN-BLUE ×1
```

### モール側への登録

セット親はモール側では「単品」として登録：
- 楽天：商品管理番号 `PEN-SET-RB`、在庫はクロスモール側で計算してモールに反映
- Amazon：item_sku `PEN-SET-RB`、quantityはクロスモール側で計算
- Yahoo!：code `PEN-SET-RB`、quantityは計算値
- Shopify：Handle `pen-set-rb`、Variant Inventory Qty は計算値

→ モール側ではセット構成情報を持たない（バラ売りの情報は別途）

## セット商品の連携事故パターン

### 1. 構成情報の設定漏れ

セット親をクロスモールに登録したが、構成情報を入れ忘れた：
- セット親の在庫が0のまま
- またはセット親に独立在庫を入れて、子が連動しない
- → セットだけ売れて、子の在庫が減らない

対応：
- 全セット商品の構成情報を点検
- 構成情報がないセット親をリストアップ

### 2. 構成数量の誤り

「2本セット」なのに構成数量1を設定：
- 子1個減算で2本セットが1個売れる扱い
- 実際の出荷は2本必要 → 子の在庫が-1される

対応：
- 構成情報の数量を再確認
- 売上明細とピッキング数で照合

### 3. 子商品のSKU紐付けミス

セット構成元のSKUが、基準商品マスタに存在しない：
- セット販売時にエラー
- またはエラーなしで子在庫が減らない

対応：
- 構成元SKUが基準SKUに存在することを確認
- 表記ゆれ（大文字小文字・ハイフン）を正規化

### 4. 連動範囲の理解不足

子の在庫を手動で変更したらセット親の販売可能数が変動：
- 操作者が「セット親だけ動くと思った」→ 実は子も連動
- 想定外の在庫変動

対応：
- セット親と子の関係を運用ドキュメント化
- 在庫変更時は影響範囲（セット親含む）を表示する設定

### 5. バラ売りとセット売りで子在庫を奪い合う

```
子: PEN-RED（在庫50）
バラ売り商品: PEN-RED（単品販売）
セット商品: PEN-SET-RB（PEN-RED ×1 + PEN-BLUE ×1）
```

バラ売りで30本売れる：
- PEN-RED 在庫：50→20
- セット親の販売可能数：min(20, 30) = 20（PEN-BLUE 30より少なくなる）

→ セット販売予定数が狂う

対応：
- バラ売りとセット売りで在庫配分を計画
- セット用に「予約在庫」を確保（stock_goods_id の使い分け等）

### 6. セット親自身に在庫を持たせる設計の事故

NG設計：
- セット親 PEN-SET-RB に独立在庫 10 を設定
- 子の在庫変動が反映されない
- セット販売で-1するが、子は減らない

→ 在庫整合が崩壊。倉庫実在庫と乖離。

正しい設計：
- セット親は在庫を持たない（または計算値）
- 子の在庫変動で自動再計算

## セット商品の検査項目

### 1. 構成情報の存在

全セット親に構成情報が登録されているか。

### 2. 構成元SKUの存在

構成情報のSKUが基準商品マスタに存在するか。

### 3. 計算値の整合

セット親の販売可能数 = min(子の在庫 / 構成数量)

```python
def calculate_set_stock(set_parent: dict, components: list[dict]) -> int:
    """
    set_parent: {sku, ...}
    components: [{sku, qty, stock}, ...]
    return: セット親の販売可能数
    """
    possible = [c["stock"] // c["qty"] for c in components]
    return min(possible) if possible else 0
```

クロスモールで表示されているセット親の販売可能数と、上記の計算値が一致するか。

### 4. モール側在庫との整合

セット親の販売可能数（計算値）が、各モールに正しく反映されているか。

### 5. 連動チェック

子の在庫変動でセット親の在庫が変わることを確認。

## セット商品の運用ベストプラクティス

### 設計フェーズ

1. **セット親は在庫を持たない設計に統一**
2. **構成情報は明確に**（数量・必要子SKU）
3. **子のSKU命名はセット親と異なるものに**（混同防止）

### 運用フェーズ

1. **新規セット商品登録時のチェックリスト**
   - 構成情報が入っているか
   - 子SKUが存在するか
   - モール側に「単品扱い」で登録したか
   - テスト販売で在庫連動を確認したか
2. **月次の在庫整合検査**
   - セット親の表示在庫と計算値の照合
3. **バラ売り＋セット売りの場合は在庫配分計画**
   - セット用予約在庫の確保

### 検査の自動化

```python
def audit_set_products(crossmall_data: dict, malls_data: dict) -> list[dict]:
    issues = []
    for set_sku, info in crossmall_data["set_products"].items():
        components = info["components"]
        # 計算値
        calc_qty = calculate_set_stock(info, components)
        # モール側在庫との比較
        for mall, stock in malls_data.items():
            mall_qty = stock.get(set_sku)
            if mall_qty is None:
                issues.append({"set": set_sku, "mall": mall, "issue": "未登録"})
            elif mall_qty != calc_qty:
                issues.append({
                    "set": set_sku,
                    "mall": mall,
                    "issue": "セット計算値と乖離",
                    "expected": calc_qty,
                    "actual": mall_qty,
                })
    return issues
```

## まとめ

- セット親は**在庫を持たない設計**にする
- 構成情報を正しく設定（子SKU + 数量）
- 子の在庫変動で自動再計算
- バラ売りとセット売りの在庫を奪い合う場合は配分計画
- 月次でセット親の表示在庫と計算値を突合
- 連携事故の多くは「構成情報の設定漏れ」または「子のSKU紐付けミス」
