# SKU紐付けマトリクスの作り方

クロスモール在庫連携の品質は「**SKU紐付け表の正確性**」に依存する。マッピングミスがあると、どれだけ綿密に連携設定を組んでも事故が起きる。

## 紐付けマトリクスの構造

### 1モール×1基準SKU の場合

| 基準SKU | 楽天SKU | Amazon SKU | Yahoo! code | Shopify SKU |
|---|---|---|---|---|
| TSH-001-BLK-S | TSH-001-BLK-S | TSH-001-BLK-S | TSH-001-BLK-S | TSH-001-BLK-S |

→ 全モール統一が理想。命名規則がモールで異なる場合のみマッピング表を別途維持。

### 命名規則が異なる場合

| 基準SKU | 楽天SKU | Amazon SKU | Yahoo! code |
|---|---|---|---|
| TSH-001-BLK-S | TSH-001-項目選択肢-黒-S | TSH-001-BS | tsh-001 (option1:黒, option2:S) |

→ 表記が異なるが意味は同じ → クロスモール側のマッピングテーブルで対応

### 1基準SKUに複数モールSKU紐付け（正常）

ある基準SKUを複数モール／複数SKUに出している場合：

| 基準SKU | 楽天SKU#1 | 楽天SKU#2（プライム用） | Amazon SKU |
|---|---|---|---|
| TSH-001 | TSH-001-RKT | TSH-001-RKT-PRIME | TSH-001 |

楽天で同一商品を「通常出品」と「プライム出品」で2SKU運用するケース。両方が基準在庫を共有。

### NG：1モールSKUが複数基準SKUに紐付き（事故源）

| 基準SKU | 楽天SKU |
|---|---|
| TSH-001 | TSH-001 |
| TSH-001-OLD | TSH-001 |

→ 楽天で `TSH-001` が売れたとき、どちらの基準SKUの在庫を減らすか不明。事故源。

## 紐付け検査の手順

### Step 1：データ取得

| ソース | 取得方法 |
|---|---|
| 基準SKU | クロスモールの商品マスタCSV |
| 楽天SKU | 楽天RMS：normal-item.csv |
| Amazon SKU | セラーセントラル：在庫レポート |
| Yahoo! code | ストアエディタ：商品CSV |
| Shopify SKU | Admin：products.csv |

### Step 2：マッピング表の構築

クロスモール側のマッピング設定を基準に、各モールで実際に存在するSKUを突合。

例：
- クロスモール基準SKU `TSH-001`
- マッピング設定：楽天SKU `TSH-001`、Amazon SKU `TSH-001`
- 楽天RMSで `TSH-001` が存在するか？ → 確認
- Amazonセラーセントラルで `TSH-001` が存在するか？ → 確認

### Step 3：検査項目

#### A. 重複紐付け検出

1モールSKUが複数基準SKUに紐付いていないか。

```python
def find_duplicate_mappings(mappings: list[dict]) -> dict:
    """
    mappings: [{base_sku, rakuten_sku, amazon_sku, ...}]
    return: {rakuten: {sku: [base_skus]}, amazon: {sku: [base_skus]}, ...}
    """
    by_mall = {"rakuten": {}, "amazon": {}, "yahoo": {}, "shopify": {}}
    for m in mappings:
        for mall in by_mall:
            sku = m.get(f"{mall}_sku")
            if sku:
                by_mall[mall].setdefault(sku, []).append(m["base_sku"])
    # 重複のみ抽出
    duplicates = {}
    for mall, skus in by_mall.items():
        for sku, base_list in skus.items():
            if len(base_list) > 1:
                duplicates.setdefault(mall, {})[sku] = base_list
    return duplicates
```

#### B. 未紐付け検出

##### 基準側にあってモール側に無い
- 出品忘れ／削除済み／そもそも出品予定なし
- 確認後、不要なら基準側マッピングを空に

##### モール側にあって基準側に無い
- 取込忘れ／未連携／別管理
- 確認後、基準SKUに紐付け or 連携対象外設定

#### C. 表記ゆれ検出

完全一致しないが類似度が高いペアを抽出：
- `TSH-001` vs `tsh-001`（大文字小文字違い）
- `TSH-001` vs `TSH_001`（記号違い）
- `TSH-001` vs `TSH-001 `（末尾空白）
- `TSH-001` vs `ＴＳＨ-001`（全角混入）

正規化後（小文字化・半角化・記号統一）に一致するペアを「表記ゆれ候補」として報告。

### Step 4：紐付けレポート

```
紐付け検査結果

⚠️ 一部モール未紐付け（出品予定？）：30件

```

## 紐付けの設計パターン

### パターン1：完全統一（推奨）

全モール・基準で同一SKU命名規則。
- メリット：マッピング表が不要、運用がシンプル
- デメリット：モール別の運用制約に縛られる

### パターン2：基準SKU独立＋モール別マッピング

基準SKUは自由命名、モール別SKUは各モールの規則に従う。
- メリット：モール別の制約を吸収
- デメリット：マッピング表の維持が必要

### パターン3：JANベース紐付け

SKUではなくJANで紐付け。
- メリット：商品アイデンティティが明確
- デメリット：JAN変更時の連携切れ、バリエーション毎のJAN必要

## 紐付け運用のベストプラクティス

### 新規商品登録時

1. 基準SKUを命名規則に従って採番
2. モール別SKUを各モールに登録
3. クロスモールにマッピング登録
4. **テスト**：1個販売 or 在庫変更で連携確認
5. 本番運用開始

### 既存商品の修正時

1. **モール側SKUは原則変更しない**（Amazonは変更不可）
2. 基準SKU変更が必要なら影響範囲を全件確認
3. マッピング表を更新
4. テスト商品で連携確認

### 月次検査

- 重複・未紐付け・表記ゆれを定例検出
- 結果をオペレーターと共有
- 修正対応の責任者を決める

## 紐付け破綻のリカバリ

### 紐付けがズレた商品の在庫再構築

1. **基準在庫を物理棚卸で確定**
2. **モール側SKUを再確認**（モール側を変えずに）
3. **クロスモール側のマッピングを修正**
4. **テスト**：商品マスタCSVで在庫を実数値登録
5. **モール側に正しい在庫が反映されるか確認**

### 全件再構築が必要なケース

- マッピング表が大規模に壊れている
- 過去の連携ログが当てにならない

→ 一旦連携停止 → モール別在庫を棚卸ベースで再確定 → 紐付け再構築 → 連携再開
（運用停止時間がかかるため、計画的に実施）
