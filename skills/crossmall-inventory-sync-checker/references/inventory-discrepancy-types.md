# 在庫ズレの分類と原因

クロスモール（および類似の在庫連携SaaS）で発生する在庫ズレの分類と、各分類の原因・典型症状・対応方針。

## 1. タイミング差ダブル販売

### 症状
- 在庫1個の商品が同時期に2モール以上で受注成立
- 基準在庫がマイナス値を取る
- どちらかの受注をキャンセルする必要

### 原因
- 連携間隔（30-60分）の隙間に同時受注
- 高速回転・希少商品で多発

### 対応
- 安全在庫の設定（1-3個）
- 連携間隔の短縮（プラン依存）
- リアルタイム連携対応モールへ移行
- 在庫1個の商品は1モール集約

## 2. SKU紐付けミス

### 症状
- モール側で売れたのに、基準在庫が減らない
- 別商品の在庫が誤って減算される
- モール側在庫と基準在庫が常に乖離

### 原因
- 紐付け表のSKU表記ゆれ
- 紐付け重複（1モールSKU → 複数基準SKU）
- モール側でSKU命名変更したがクロスモールに反映漏れ
- 新規商品の紐付け設定漏れ

### 対応
- 紐付け表の総点検
- 重複検出機能の活用
- 新規商品登録フローに紐付け確認を組み込む
- 表記ゆれの正規化

## 3. 手動操作の上書き事故

### 症状
- モール側で在庫を手動変更した直後にクロスモールが上書き
- または、クロスモール側で手動変更したら次回同期で元に戻る

### 原因
- モール側で在庫直接編集→クロスモール同期で書き戻し
- 連携を停止せずに手動操作
- 仕入入荷の二重登録（クロスモール側＋モール側）

### 対応
- 在庫変更は**クロスモール（または倉庫マスタ）のみ**で行う
- どうしてもモール側で変更が必要な場合は連携停止→変更→再開
- 仕入入荷はクロスモール側に統一

## 4. セット構成元の連動失敗

### 症状
- セット商品の販売可能数が実態と合わない
- 子商品の在庫変動がセット親に反映されない
- 在庫0の子があるのにセットが販売可能と表示

### 原因
- セット商品の構成情報設定漏れ
- セット親の在庫が独立管理になっている
- 連携先モール側でセット商品をバラ売り商品として登録

### 対応
- セット構成情報の総点検
- 親在庫 = min(子在庫) ÷ 構成数 で再計算
- セット商品をモール側で「単品」として登録（在庫はクロスモール側で計算）

## 5. 受注取込遅延

### 症状
- あるモールで売れたのに、クロスモールへの取込が遅い
- その間に他モールでも売れる → ダブル販売

### 原因
- モール側API障害
- クロスモール側の同期処理遅延
- 受注取込の頻度設定が低い

### 対応
- 各モールの受注取込頻度を確認・短縮
- 同期失敗ログの監視
- 大量受注時の取込遅延対策（バッチ処理→ストリーム処理）

## 6. バリエーション親子の不整合

### 症状
- バリエーション親の在庫表示が子の合計と合わない
- 親が独立在庫を持っていて二重カウント
- 子のうち1つが在庫切れでも親が販売可能

### 原因
- バリエーション設計時の親在庫の扱いが曖昧
- 子の追加削除時に親在庫の再計算がされない

### 対応
- バリエーション親は在庫を持たない設計に統一
- 子の合計または min(子) を親在庫の表示用に算出
- 在庫切れ子の自動非公開設定

## 7. マイナス在庫の出力

### 症状
- 基準在庫がマイナス値（-1, -2 等）
- モール側に「在庫切れ」の代わりに「-1」が表示される

### 原因
- ダブル販売事故の結果
- 連携設定でマイナスをそのままモールに送る設定

### 対応
- クロスモール側でマイナス在庫を0に変換する設定
- モール側で「マイナス受信時は0扱い」の設定
- マイナス発生時のアラート設定

## 8. 仕入入荷の反映遅延

### 症状
- 仕入で入荷したのにモール側で売り切れのまま
- 入荷登録から数時間〜1日反映されない

### 原因
- 入荷登録の反映タイミング
- WMSとクロスモールの連携遅延
- 入荷登録漏れ

### 対応
- 入荷登録フローの標準化
- 日次の在庫スナップショット比較
- 緊急時の手動反映手順を整備

## 9. 返品・キャンセルの在庫戻し漏れ

### 症状
- 返品処理後も基準在庫が増えない
- キャンセル受注の在庫が戻されない

### 原因
- 返品登録時の在庫戻し設定漏れ
- 取消・キャンセル処理の自動化不十分

### 対応
- 返品・キャンセル時の在庫戻しを自動化
- 手動戻しが必要な場合のチェックリスト整備

## 10. 倉庫実在庫との乖離

### 症状
- 月次棚卸で実在庫とクロスモール在庫が合わない
- 商品により+5、-3 などのズレ

### 原因
- 出荷ピッキング時の誤出荷
- 仕入入荷の数量誤り
- 検品漏れ・破損品の未処理
- 棚卸時の数え漏れ

### 対応
- 月次棚卸を必ず実施
- 差分を分析（特定商品に偏るか／全般に出るか）
- 業務フローの改善（出荷時のスキャン徹底等）

## ズレの優先度評価

| 優先度 | 種類 |
|---|---|
| 🚨 即時 | ダブル販売事故（売り越し） |
| 🚨 即時 | 紐付け重複（事故の前兆） |
| ⚠️ 24h以内 | 手動操作の上書き、マイナス在庫の継続出力 |
| ⚠️ 24h以内 | 受注取込の連続失敗 |
| 📋 週次 | バリエーション親子の不整合、セット連動失敗 |
| 📋 月次 | 倉庫実在庫との乖離（棚卸） |

## 検出方法のまとめ

### 自動検出可
- 紐付け重複・未紐付け（マッピング表の検査）
- 在庫差分（基準在庫 vs 各モール在庫の比較）
- マイナス在庫
- バリエーション親子の不整合
- セット親販売可能数の再計算

### 手動検出推奨
- 倉庫実在庫との乖離（棚卸）
- 業務フロー上のミス（誤出荷等）
- 設定ミス（安全在庫が低すぎる等）

## 検出スクリプト例

```python
def check_inventory_diff(reference: dict, malls: dict) -> list[dict]:
    """
    reference: {sku: stock_qty}
    malls: {mall_name: {sku: stock_qty}}
    return: 差分リスト
    """
    issues = []
    for sku, ref_qty in reference.items():
        for mall, stock in malls.items():
            mall_qty = stock.get(sku)
            if mall_qty is None:
                issues.append({"sku": sku, "mall": mall, "issue": "未紐付け"})
            elif mall_qty != ref_qty:
                issues.append({
                    "sku": sku,
                    "mall": mall,
                    "issue": "在庫差分",
                    "reference": ref_qty,
                    "mall_qty": mall_qty,
                    "diff": mall_qty - ref_qty,
                })
    return issues
```

差分の閾値は許容誤差を踏まえて設定（連携誤差0-2程度、超えたら要調査）。
