# 連携タイミング・再発防止運用

## 連携の基本動作

### 在庫連携（基準→各モール）

クロスモールが基準在庫を各モールに書き戻す方向。
- 標準的な間隔：30-60分
- プランによって短縮可能（リアルタイム対応プランあり）
- 同期失敗時の再試行設定あり

### 受注連携（各モール→基準）

各モールの受注をクロスモールが取り込む方向。
- 楽天：数分～10分
- Amazon：数分（SP-API）
- Yahoo!：数分
- Shopify：数分～即時（Webhook対応）

### 受注取込→在庫減算→各モール反映 の流れ

```
楽天で1個受注
  ↓ (数分)
クロスモールが受注取込
  ↓ (即時)
基準在庫が-1
  ↓ (最大30-60分)
Amazon/Yahoo!/Shopifyの在庫が-1反映
```

→ **楽天で売れてから他モールに反映されるまで30-60分の遅延**がある。

## ダブル販売が起きる時間窓

```
T+0: 楽天とAmazon両方で在庫1個と表示
T+0~T+30分: 楽天で受注成立、まだクロスモール未取込
T+5分: Amazon受注成立（その時点でAmazon在庫1なのでOK）
T+10分: クロスモール楽天受注取込 → 基準在庫 1 - 1 = 0
T+20分: クロスモールAmazon受注取込 → 基準在庫 0 - 1 = -1
T+30分: クロスモール在庫同期 → 楽天0、Amazon0、基準-1
```

→ ダブル販売事故。**30分の連携間隔では在庫1個の商品はリスク高**。

## 連携間隔の短縮

### プランによる対応

- 標準プラン：30-60分
- 上位プラン：5-15分
- リアルタイム：API直接連動

### 短縮のメリット
- ダブル販売リスク低減
- 在庫情報の鮮度向上

### 短縮のデメリット
- API呼出制限に近づく（モール側のレート制限）
- 同期負荷増大
- プランコスト増

### 短縮を検討すべき条件
- 月次のダブル販売事故が3件以上
- 高速回転商品（日次10個以上）が多い
- 高単価商品の在庫を多モール展開

## 同期失敗の検知

### よくある失敗原因

1. **モール側API障害**
   - 楽天RMS定期メンテナンス（深夜帯）
   - Amazon SP-API一時障害
2. **クロスモール側のサーバー負荷**
3. **大量商品の同期処理タイムアウト**
4. **認証情報の期限切れ**（トークン更新忘れ）
5. **モール側でアカウントが一時停止**

### 監視項目

| 項目 | 頻度 | 通知先 |
|---|---|---|
| 各モールの最終同期時刻 | 1時間毎 | 管理者 |
| 連携失敗エラーログ | リアルタイム | 管理者 |
| 基準在庫マイナス値 | 即時 | 管理者＋オペレーター |
| 大量在庫変動（10%超） | 即時 | 管理者 |

### アラート設定

クロスモール側で：
- 連携失敗 → メール／Slack通知
- マイナス在庫 → 即時通知
- 認証期限切れ → 期限7日前通知

## 受注の取込フロー

### 標準フロー

1. モール側で受注成立
2. クロスモールがAPI/Webhookで受注取込
3. 基準在庫を減算
4. WMSへ出荷指示
5. 各モール在庫を更新（次回同期で反映）

### 失敗時のリカバリ

- 取込失敗ログを毎日確認
- 失敗した受注は手動で再取込
- 在庫が連動していない受注がないか確認

## 棚卸と整合確認

### 月次棚卸の手順

1. **物理棚卸を実施**（倉庫スタッフ）
2. **クロスモール基準在庫の出力**
3. **WMS在庫データの出力**（別倉庫管理システムを使っている場合）
4. **3者の照合**
   - 物理棚卸 vs クロスモール基準
   - 物理棚卸 vs WMS
   - クロスモール vs WMS
5. **差分の分析と修正**

### 差分の原因分類

| 差分パターン | 推定原因 | 対応 |
|---|---|---|
| 物理>システム | 入荷登録漏れ | 入荷フロー見直し |
| 物理<システム | 誤出荷／盗難／破損 | 出荷検品強化 |
| 特定商品に偏る | 商品マスタ／紐付けミス | マスタ修正 |
| 全般に少しずつ | 連携誤差 | 安全在庫見直し |

## 業務フロー設計

### 在庫変更フロー（推奨）

```
1. クロスモールまたは倉庫システムで在庫変更
   ↓
2. クロスモール → 各モール同期（30-60分以内）
   ↓
3. 各モール側で在庫反映確認（任意）
```

NG：モール側で直接在庫変更 → クロスモールに矛盾発生

### 仕入入荷フロー

```
1. 仕入入荷 → 倉庫検品
   ↓
2. WMSまたはクロスモールに入荷登録（数量入力）
   ↓
3. 基準在庫が+N
   ↓
4. 各モール同期 → モール在庫+N
```

### 返品・キャンセルフロー

```
1. モールで返品/キャンセル登録
   ↓
2. クロスモールが取込
   ↓
3. 基準在庫が+N
   ↓
4. 各モール同期 → モール在庫+N
```

注：商品が「再販可能」か「廃棄」かで在庫戻し動作が異なる場合あり。

## 緊急時対応

### ダブル販売事故が発生したら

1. **顧客にすぐ連絡**（電話＋メール）
2. **代替提案**（類似商品／再入荷待ち／全額返金＋お詫び）
3. **モール側で受注キャンセル処理**（販売者起因キャンセルになる場合あり）
4. **原因分析**：なぜ事故が起きたか
5. **再発防止**：該当商品の安全在庫見直し、連携設定確認

### 大規模在庫ズレが発覚したら

1. **連携を一時停止**（クロスモール管理画面）
2. **物理棚卸を実施**
3. **基準在庫を物理棚卸値で確定**
4. **モール側在庫を手動修正または連携再開で反映**
5. **原因分析→根本原因対応**

## 再発防止の運用設計

- 監視・アラートを自動化
- オペレーターの教育（在庫を直接モール側で変更しない）
- 月次の整合検査を定例化
- 高単価／希少品はリアルタイム連携または1モール集約
- セット商品の在庫設計をドキュメント化
- 新規商品登録時のチェックリスト整備
