# クロスモール在庫連携 ケース別実例

## ケース1：ダブル販売事故の検出と対応

### 状況

`TSH-005-BLK-S` の在庫1個。3モール（楽天／Amazon／Yahoo!）で販売中。同期間隔30分。

### イベントログ

```
14:00 各モール在庫表示：楽天1、Amazon1、Yahoo!1、基準1
14:08 楽天で受注成立（1個）
14:14 Amazon SP-API取込：Amazonでも受注成立（1個）
14:20 クロスモール受注取込（楽天）→ 基準在庫 1 - 1 = 0
14:30 クロスモール定時同期 → 楽天0、Amazon0、Yahoo! 0
14:32 クロスモール受注取込（Amazon）→ 基準在庫 0 - 1 = -1
14:35 アラート発火：マイナス在庫検出
```

### 検査結果

| SKU | 基準在庫 | 楽天 | Amazon | Yahoo! | ステータス |
|---|---|---|---|---|---|
| TSH-005-BLK-S | -1 | 0 | 0 | 0 | 🚨 ダブル販売事故 |

### 対応

1. **緊急対応**
   - どちらの受注を優先するか判断（受注時刻・顧客ランク等）
   - 後の受注を「在庫不足のためキャンセル」処理
   - 顧客に電話＋メールで謝罪、代替商品提案

2. **再発防止**
   - `TSH-005-BLK-S` の安全在庫を1に設定（在庫1個なら全モールで「在庫切れ」表示になるが、ダブル販売は防げる）
   - 在庫1個で複数モール展開する商品は、安全在庫を考慮した運用ルールに統一
   - 高速回転商品（直近7日販売数20以上）の安全在庫を一括見直し

3. **顧客対応の標準化**
   - お詫びクーポン（500円相当）
   - 代替商品の優先案内
   - 次回利用時の優遇案内

## ケース2：紐付け重複の検出

### 入力

クロスモール SKU紐付け表（500件中、抜粋）：

| 基準SKU | 楽天SKU | Amazon SKU | Yahoo! code |
|---|---|---|---|
| TSH-001 | TSH-001 | TSH-001 | TSH-001 |
| TSH-001-OLD | TSH-001 | （空） | （空） |
| PEN-RED | PEN-RED | PEN-RED | PEN-RED |
| PEN-RED-V2 | PEN-RED | PEN-RED-V2 | （空） |

### 検出

**楽天SKU `TSH-001`** が基準SKU `TSH-001` と `TSH-001-OLD` の2つに紐付け（重複）
**楽天SKU `PEN-RED`** が基準SKU `PEN-RED` と `PEN-RED-V2` の2つに紐付け（重複）

### 事故シナリオ

楽天で `TSH-001` が1個売れる：
- クロスモールが「どちらの基準SKUに減算するか」判断できない
- エラー、または誤った基準SKUから減算
- 在庫整合が崩れ、棚卸時に乖離発覚

### 対応

1. **モール側の実態確認**
   - 楽天RMS で `TSH-001` が現役か確認
   - もし `TSH-001-OLD` が廃番なら紐付けを削除
   - 楽天で `PEN-RED` と `PEN-RED-V2` の関係を整理

2. **紐付け修正**
   - `TSH-001-OLD` の楽天紐付けを空に
   - `PEN-RED-V2` の楽天紐付けを空に（または楽天側でSKU別に出品）

3. **再発防止**
   - 新規商品登録時のバリデーション：楽天SKUに重複がないかチェック
   - 月次の紐付け検査を定例化

## ケース3：セット商品の連動失敗

### 状況

「赤ペン2本セット」「赤ペン3本セット」を運用中。

セット親 `PEN-SET-R2`：
- クロスモールで構成情報設定済み（PEN-RED ×2）
- 各モールで「単品扱い」で登録

セット親 `PEN-SET-R3`：
- クロスモールに登録されているが**構成情報が空**
- 独立在庫50を持っている

### 検出

検査結果：
- `PEN-SET-R2`：構成情報あり、子の在庫から計算値32（PEN-RED 65 / 2）
- `PEN-SET-R3`：構成情報なし、独立在庫50
- 楽天で `PEN-SET-R3` が10個売れた → 独立在庫 50→40
- しかし `PEN-RED` の在庫は減らない
- 出荷時に「赤ペン30本必要」だが在庫が65のまま → 実在庫との乖離

### 対応

1. **`PEN-SET-R3` の構成情報を設定**
   - PEN-RED ×3
2. **独立在庫を解除**
   - セット親は計算値で在庫表示するよう設定
3. **在庫の実数値合わせ**
   - 物理棚卸 → 基準在庫を実数値登録
4. **過去の出荷記録確認**
   - PEN-RED の在庫を本来あるべき値に修正

### 再発防止

- セット商品登録時のチェックリスト：
  - [ ] 構成情報を入力したか
  - [ ] 構成元SKUが存在するか
  - [ ] 独立在庫は0または無効化したか
  - [ ] テスト販売で連動確認したか
- 月次でセット商品の構成情報・計算値・モール在庫を突合

## ケース4：受注取込の遅延

### 状況

Yahoo!ショッピングからの受注取込が、過去24時間で平均40分遅延（通常は5分）。

### 検査結果

クロスモール同期ログ：

| モール | 最終取込時刻 | 平均遅延（過去24h） | 失敗件数 |
|---|---|---|---|
| 楽天 | 14:30 | 3分 | 0 |
| Amazon | 14:28 | 5分 | 0 |
| Yahoo! | 13:50 | 40分 | 接続タイムアウト 3件 |
| Shopify | 14:33 | 2分 | 0 |

### 原因分析

- Yahoo!ストア側のAPI障害？
- クロスモール側のYahoo!連携設定の問題？
- ネットワーク経路の問題？

### 対応

1. **Yahoo!ストアエディタで受注状況確認**
   - Yahoo!側で受注は正常に発生しているか
2. **クロスモール公式サポートに問合せ**
   - 連携障害の有無確認
3. **緊急対応**
   - 手動でYahoo!受注を取込
   - Yahoo!在庫を一時的に低く設定（オーバーセール予防）
4. **本格対応**
   - 障害が解消するまで監視
   - 解消後、遅延中の受注で在庫不整合がないか確認

### 監視強化

- Yahoo!連携の同期成功率を日次モニタ
- 30分以上の遅延でアラート発火

## ケース5：バリエーション親子の不整合

### 状況

商品 `TSH-001`（バリエーション親）配下に9SKU（黒/白/グレー × S/M/L）。

### 検査結果

クロスモール商品マスタ：

| SKU | 種別 | 在庫 |
|---|---|---|
| TSH-001 | バリエーション親 | 50（独立在庫設定） |
| TSH-001-BLK-S | 子 | 6 |
| TSH-001-BLK-M | 子 | 7 |
| TSH-001-BLK-L | 子 | 5 |
| TSH-001-WHT-S | 子 | 4 |
| TSH-001-WHT-M | 子 | 8 |
| TSH-001-WHT-L | 子 | 3 |
| TSH-001-GRY-S | 子 | 2 |
| TSH-001-GRY-M | 子 | 6 |
| TSH-001-GRY-L | 子 | 4 |

### 検出

- 子の合計：6+7+5+4+8+3+2+6+4 = 45
- 親の独立在庫：50
- → **二重カウント疑い**（親が独立在庫を持っており、子も別途在庫を持っている）

### 問題

- モール側に「商品全体の在庫」を表示する場合、50か45かどちらを使うか
- 楽天の「項目選択肢別在庫」では各子の在庫が表示される
- 一覧画面で「在庫50」と表示されると誤解を招く
- 在庫評価額が水増しされる

### 対応

1. **バリエーション親は在庫を持たない設計に変更**
   - 親の独立在庫を0に
   - 表示在庫は子の合計または min(子) を計算値として
2. **棚卸との照合**
   - 物理棚卸：黒S=6, 黒M=7, ...（個別カウント）
   - 子の在庫を物理棚卸値で確定
3. **モール側の確認**
   - 楽天：項目選択肢別在庫が正しく表示されているか
   - Amazon：子ASIN毎の在庫が正しいか

### 再発防止

- バリエーション設計のドキュメント化：「親は在庫を持たない」
- 新規バリエーション商品登録時のチェックリスト
- 月次の親子在庫整合検査
